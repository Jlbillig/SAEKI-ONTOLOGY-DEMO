# RDF Graph Export

FactoryTrace stores all production events as RDF triples in an in-process
RDFLib graph. This document explains how to access the raw graph data,
what the Turtle serialization format looks like, and how this data would
be consumed by an AI agent or downstream system.

---

## The `/graph/export` Endpoint

```
GET http://localhost:8000/graph/export
```

Returns the full graph serialized as Turtle (`.ttl`), the standard
human-readable RDF format. This is the same format as the ontology file
at `ontology/factory_trace_ontology.ttl`.

### Example response (truncated)

```json
{
  "turtle": "@prefix ft: <https://example.org/factory-trace#> .\n ..."
}
```

## What a Failed Part Looks Like in Turtle

After running the demo scenario and investigating PART-1000-015, the
relevant slice of the graph looks like this in Turtle:

```turtle
@prefix ft: <https://example.org/factory-trace#> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

# The part itself
ft:Part_PART_1000_015 a ft:Part ;
    ft:partId "PART-1000-015" ;
    ft:processedMaterialBatch ft:MaterialBatch_BATCH_B ;
    ft:hasInspectionResult ft:Event_EVT_000061 .

# The inspection result
ft:Event_EVT_000061 a ft:InspectionResult ;
    ft:eventId "EVT-000061" ;
    ft:inspectionStatus "fail" ;
    ft:deviationType "surface_finish_out_of_tolerance" ;
    ft:timestampValue "2026-05-11T09:33:00Z"^^xsd:dateTime .

# The milling operation that produced the part
ft:Operation_RUN_2026_001_PART_1000_015_milling a ft:MillingOperation ;
    ft:actsOnPart ft:Part_PART_1000_015 ;
    ft:performedByMachine ft:Machine_CNC_02 ;
    ft:usesTool ft:Tool_TOOL_11 ;
    ft:partOfProductionRun ft:ProductionRun_RUN_2026_001 .

# The machine
ft:Machine_CNC_02 a ft:CNCMachine ;
    ft:machineId "CNC-02" ;
    ft:hasTelemetryEvent ft:Event_EVT_000060 .

# The telemetry event showing the anomaly
ft:Event_EVT_000060 a ft:TelemetryEvent ;
    ft:eventId "EVT-000060" ;
    ft:timestampValue "2026-05-11T09:31:00Z"^^xsd:dateTime ;
    ft:vibrationMMs "6.5"^^xsd:decimal ;
    ft:temperatureC "85.75"^^xsd:decimal ;
    ft:associatedWithMachine ft:Machine_CNC_02 ;
    ft:associatedWithPart ft:Part_PART_1000_015 .

# The alarm event generated by the anomaly
ft:Event_ALARM_EVT_000060 a ft:AlarmEvent ;
    ft:eventId "ALARM_EVT-000060" ;
    ft:timestampValue "2026-05-11T09:31:30Z"^^xsd:dateTime ;
    ft:associatedWithMachine ft:Machine_CNC_02 ;
    ft:associatedWithPart ft:Part_PART_1000_015 .

# The quality deviation node
ft:QualityDeviation_EVT_000061 a ft:QualityDeviation ;
    ft:deviationType "surface_finish_out_of_tolerance" ;
    ft:associatedWithPart ft:Part_PART_1000_015 ;
    ft:timestampValue "2026-05-11T09:33:00Z"^^xsd:dateTime .

# The root cause hypothesis written when investigation was run
ft:RootCauseHypothesis_RCH_PART_1000_015 a ft:RootCauseHypothesis ;
    ft:associatedWithPart ft:Part_PART_1000_015 ;
    ft:associatedWithMachine ft:Machine_CNC_02 ;
    ft:associatedWithTool ft:Tool_TOOL_11 .

# The material batch
ft:MaterialBatch_BATCH_B a ft:MaterialBatch ;
    ft:batchId "BATCH-B" .

# The cutting tool
ft:Tool_TOOL_11 a ft:CuttingTool ;
    ft:toolId "TOOL-11" .
```

## Why This Matters for AI Agents

The Turtle representation above is what an AI agent receives when it
queries the graph for context about a failed part. Compare these two
approaches:

### Approach A: Unstructured log dump (naive)

```
EVT-000058: production_start CNC-02 PART-1000-015 TOOL-11 BATCH-B milling started
EVT-000059: telemetry CNC-02 PART-1000-015 spindle=8500 feed=420 vib=6.5 temp=85.75 running
EVT-000060: operation_complete CNC-02 PART-1000-015 completed
EVT-000061: inspection_result INSPECTION-01 PART-1000-015 fail surface_finish_out_of_tolerance
[... 116 more lines ...]
```

Token cost for 120 events: approximately 3,000–5,000 tokens.
The agent must reason over noise to find the causal chain.

### Approach B: Targeted SPARQL query over the knowledge graph

The investigation query returns exactly the triples shown above —
the part, its inspection result, the operation, the machine, the tool,
the telemetry event, the alarm, the deviation, and the hypothesis.

Token cost: approximately 400–600 tokens.
The causal chain is already explicit in the graph structure.

Published research (ACL 2025 workshop, TERAG framework) demonstrates
**80–97% token reduction** when using graph-based retrieval versus
naive context loading. For an AI agent running hundreds of manufacturing
queries per day, this translates directly into inference cost savings.

## Relationship to the R2RML Mapping

The `ontology/r2rml_mapping.ttl` file in this repository defines how
a relational database with this same schema would produce identical
triples. This means the semantic layer is not tied to the event-driven
ingestion path — historical data from an existing MES or ERP can be
lifted into the graph using a standard R2RML processor (e.g. RML Mapper,
Ontop, or Morph-KGC) without modifying any application code.

This is the production integration path: live events flow through
`semantic_mapper.py`, and historical bulk data flows through R2RML.
Both produce triples that conform to the same ontology and are
queryable with the same SPARQL queries.
